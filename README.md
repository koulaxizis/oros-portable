# orOS Portable

Run [orOS](https://useoros.online) from a USB stick on any Windows or Linux PC, with or without internet. MIT, free forever.

## Which edition?

| | **Full** (`orOS-Portable`) | **Lite** (`orOS-Portable-lite`) |
|---|---|---|
| Size | ~455 MB download, 1–1.5 GB on the stick | ~36 MB |
| Browser | bundled ungoogled-chromium (Windows + Linux) | an installed Chromium, Brave, Edge or Chrome |
| Works on | any Windows 10/11 or 64-bit Linux PC | Windows (Edge); Linux only with a Chromium-family browser |
| Google / Microsoft | none | often runs inside Edge or Chrome |

Not sure? Take the full edition. Both run from the stick and keep data on it. Stick: 32 GB or more recommended (64 GB ideal), 8 GB minimum, formatted as NTFS. The release page has the same table in Greek.

## How it works

The stick holds a small launcher (`orOS.exe` / `orOS`), the orOS web app (`app/`) and, in the full edition, a portable [ungoogled-chromium](https://github.com/ungoogled-software/ungoogled-chromium) (`browser/`). The launcher:

1. serves `app/` from `http://localhost:47800/` (loopback only, read-only, other Host names refused);
2. opens the browser in app mode with its profile in `data/profile/` on the stick;
3. stops the server when the window closes.

The address never changes, because the browser ties stored data to it. When port 47800 is taken at start (`launcher/portbusy.go`), the launcher waits up to 10 seconds for an orOS that is closing, joins an orOS that answers (window or tray), offers to close an earlier orOS launcher that holds the port but no longer answers, and otherwise names the program that holds it (Windows: `GetExtendedTcpTable`; Linux: `/proc`), orOS Drive waiting for a Dropbox sign-in, or a port range Windows reserved for itself (Hyper-V, WSL, Docker; `net stop winnat` / `net start winnat` frees it). orOS's service worker caches the whole app, so it works offline like the installed PWA. Encrypted Dropbox sync works as on useoros.online when online.

The lite edition has no bundled browser and uses an installed Chromium, Brave, Edge or Chrome, with a separate `data/profile-system/` profile (a profile from a newer Chromium may not open in an older one). If the bundled browser fails to start (for example a Linux system that blocks its sandbox), the launcher falls back to an installed one.

### System in Quick settings (full edition and installers)

The full edition and the installers carry orOS USB's System extension (`system/`, fetched from [oros-usb](https://github.com/koulaxizis/oros-usb) `system/extension` by `scripts/build.sh`). The bundled browser loads it with `--load-extension` (Edge and Chrome refuse that flag, so the lite edition and installed browsers go without), and the launcher itself is its native messaging host `online.useoros.system` (`launcher/syshost.go`): Chromium starts `orOS chrome-extension://…/` for each message. On Linux the host manifest lives in the profile (`NativeMessagingHosts/`); on Windows in the data folder with a key under `HKCU\Software\Chromium\NativeMessagingHosts`, which a portable copy takes away again when orOS closes.

The extension then shows in orOS's Quick settings what this computer has (the `caps` in `status`): sound and mute (PipeWire/PulseAudio; Windows Core Audio), screen brightness (logind backlight; WMI on laptops), battery, sleep, restart and shut down of the computer (each confirmed), leaving orOS, full screen or a window, a report zip in Downloads, and "Update orOS" (downloaded by a detached `orOS update-stage` into `app.next`, swapped in at the next start; on a stick and, since 2026-11-07, in the installed apps too, as a way to check at once; since 2026-11-28 the stick also checks by itself). The stick opens orOS in full screen and the installed apps in a window; the choice is kept in `data/session.json`. Short runs (the host, the update download) log to `system.log` so the window's `launcher.log` stays whole.

Internet window (`launcher/sysweb.go`): the **Internet** button next to the System button opens a normal window of the bundled browser (tabs, address bar, DuckDuckGo as the start page) in orOS's own profile (`<user folder>/profile`), so it joins the browser that shows orOS. That browser starts with the System extension, the orOS add-on (`addon/`: koulaxizis/oros `extension/`, copied by oros-usb's `scripts/addon.sh` with its orOS address preset to `http://localhost:47800/`, so it fills and saves Passwords logins, cards and addresses on web pages) and uBlock Origin Lite (`ubol/`, fetched with oros-usb's `scripts/ubol.sh`; where the program folder is read-only, the AppImage and the .deb, it runs from a copy in the data folder, because Chromium writes its indexed filter rules into the extension's folder), in one `--load-extension` list. Sites share the browser's storage with orOS, as with orOS in a tab of any browser. The browser never offers to save passwords, addresses or cards (`seedNoSaving` in `launcher/window.go` sets Chromium's `credentials_enable_service`, `credentials_enable_autosignin`, `profile.password_manager_enabled`, `autofill.profile_enabled` and `autofill.credit_card_enabled` to false in orOS's own profiles before each start, as orOS USB does through its managed policy); orOS Passwords and the orOS add-on keep them. Up to 0.6.0 the Internet window had its own profile in `data/web`; its sign-ins start over once and the folder is no longer used. The lite edition has no button: an installed browser is already at hand.

Extensions from the Chrome Web Store, and keeping them away from orOS (`launcher/extpolicy.go`): ungoogled-chromium has no "Add" button on the store and does not update extensions that came from there, so the full edition and the installers also load [chromium-web-store](https://github.com/NeverDecaf/chromium-web-store) (`webstore/`, MIT, NeverDecaf; fetched by `scripts/webstore.sh` from its latest GitHub release and checked against the SHA-256 GitHub lists) and start the bundled browser with ungoogled-chromium's `--extension-mime-request-handling=always-prompt-for-install`, so the store's pages get an "Add to Chromium" button and installed extensions are checked for updates. The browser reaches Google only when the user installs or updates something from the store. That is how a user adds a VPN extension (see [Private browsing](PRIVATE-BROWSING.md)). Since the Internet window shares orOS's profile, an extension allowed on all sites could read an unlocked orOS, so on Windows the launcher writes Chromium's `ExtensionSettings` policy for the user (`HKCU\Software\Policies\Chromium`): `runtime_blocked_hosts` `*://localhost`, `*://127.0.0.1` and `*://*.useoros.online` for every extension, and an entry without it only for the System extension and the orOS add-on, whose IDs come from the keys in their manifests (oros-usb `scripts/addon.sh` gives the add-on one; without a key no policy is written, so the add-on is never locked out). A value someone else set stays untouched. A portable copy takes the value back when orOS closes; the desktop apps keep it, as they keep the native host's key (it applies to other Chromium-branded browsers of that user too, never to Edge, Chrome or Brave). Linux reads Chromium policies only from `/etc`, which a stick cannot write, so there the guide warns instead. orOS USB has the same policy in its image.

Tor (`launcher/tor.go`, `tor_other.go`, `tor_windows.go`): the **Tor** button next to Internet opens the official [Tor Browser](https://www.torproject.org/) in its own window, as on orOS USB. orOS does not carry it: the first press (after a question) runs a detached `orOS tor --fetch`, which reads Tor Browser's `downloads.json` (https addresses on torproject.org only), downloads the 64-bit build for this system with its `.asc`, and checks the OpenPGP signature in the launcher itself (ProtonMail go-crypto; no gpg needed) against Tor Browser Developers' key, which the build puts next to the launcher (`tor-browser-developers.gpg`, oros-usb's `scripts/tor-key.sh`) and whose fingerprint `EF6E286DDA85EA2A4BA7DE684E2C6E8793298290` is pinned in the code. When that key cannot check a release (an expired or new subkey on an older stick), the key is fetched again from torproject.org's Web Key Directory or keys.openpgp.org and used only with the same fingerprint. A download that fails is deleted and never run. Linux: the `.tar.xz` is unpacked in Go (names and links that would leave the folder are refused; on FAT or exFAT a link becomes a copy). Windows: the official installer runs silently (`/S /D=<folder>`), and the shortcuts and Add or remove programs entry it makes are removed again (a Tor Browser the person installed keeps its own). It goes to `<user folder>/tor/tor-browser` (each user has their own; the guest has no Tor button), is swapped in only when complete, and from then on starts at once (`orOS tor --run`, which holds `tor/open.lock` while the window is open, so the extension brings a full-screen orOS back when it closes) and updates itself. `tor.status` gives `installed`, `running` (downloading), `open` and the progress (`tor.json`); `tor.remove` deletes the user's Tor Browser when it is neither open nor downloading. About 1 GB must be free. `OROS_NO_TOR=1` hides the button. CI downloads and installs the real Tor Browser on Linux and Windows.

Claude desktop (`launcher/claude.go`, `claude_other.go`, `claude_windows.go`; CLAUDE-1): the System extension's **Claude desktop** section and orOS's Settings › Connected services › Claude (DOM event `oros-claude`, attributes `data-oros-sys-claude` / `-why`, as on orOS USB) install Anthropic's [Claude desktop](https://claude.com/download) on this computer when the person asks; orOS never carries it (Anthropic's proprietary app). `caps.claude` is set for every user but the guest where this computer can run it. Windows: `winget install --id Anthropic.Claude -e --silent` (winget checks Anthropic's installer against its manifest's SHA-256); `claude.open` starts it through its Start menu entry (`Get-StartApps`, `shell:AppsFolder`), `claude.remove` runs `winget uninstall`; without winget it is not offered and Settings links to Anthropic's download page. Linux (where `dpkg-deb` and `ldd` exist, amd64 or arm64: the Debian and Ubuntu systems Anthropic supports): the same code as orOS USB reads Anthropic's apt repository like apt (InRelease signature against the key pinned by fingerprint `31DDDE24DDFAB679F42D7BD2BAA929FF1A7ECACE`, fetched from downloads.claude.ai; then `Packages` and the `.deb` by their signed SHA-256), unpacks it without root into `~/.local/share/oros-claude` and needs every library it uses to be on the computer. The download runs in a detached `orOS claude --fetch` holding `<user folder>/claude.lock`; progress in `claude.json`. `OROS_NO_CLAUDE=1` hides it. **Beside orOS** (`claude_side*.go`): `claude.open` and a finished install run a detached `orOS claude --open`, which starts Claude desktop, waits up to 30 s for its window and puts it on the right half of the work area with orOS on the left. Windows finds both windows by their programs (Claude's `claude.exe`; orOS = the largest window of a program under the launcher's folder) and moves them with `SetWindowPos`; Linux does the same under X11 with `wmctrl` (`-lpG`, `-d`, `-e`). Under Wayland, without wmctrl, or with orOS in full screen, Claude simply opens as before.

Local AI (`launcher/ai.go`): the System extension's **Local AI** section (System › Local AI, and "Install local AI" in orOS's Assistant) installs [Ollama](https://github.com/ollama/ollama) and an open [Qwen3](https://github.com/QwenLM/Qwen3) model (Apache-2.0), as on orOS USB. orOS does not carry them: the build pins the latest Ollama release for each system with its SHA-256 (`ollama-linux.json`, `ollama-windows.json`, oros-usb's `scripts/ollama.sh`, which checks GitHub's digest against the release's `sha256sum.txt`), and the button runs a detached `orOS ai --fetch --model <m>`. Linux: the `.tar.zst` is unpacked while it streams and hashed on the way; Windows: the `.zip` is kept until its SHA-256 matches, then unpacked. Only the program, the processor libraries and the Vulkan folder are kept (about 120 MB; CUDA and ROCm are skipped, Vulkan reaches AMD, Intel and NVIDIA cards through the computer's own driver). The model comes through Ollama's own pull (digest-checked), chosen by memory: Small `qwen3:1.7b` under 7 GiB, Medium `qwen3:4b` under 14 GiB, Large `qwen3:8b` above (a FAT32 stick cannot hold the 8b file, so it is not offered there). Everything is in `<data>/ai` (the stick's `data/ai`, or `%LOCALAPPDATA%\orOS\ai` and `~/.local/share/oros/ai` when installed), shared by every user; only the owner (or everyone, without users) installs or removes, never the guest. Ollama listens on `127.0.0.1:11434` only, lets in only the orOS page (`OLLAMA_ORIGINS`), `OLLAMA_NO_CLOUD=1`, one model and one answer at a time, and its key and caches stay in that folder (`HOME`/`USERPROFILE`). The launcher that serves orOS starts it with the server and stops it with the server (`orOS ai --stop` stops only the Ollama whose program is in that folder, found by its port), so a stick can be unplugged; the Windows uninstaller runs it too. An Ollama the person installed is used as it is when it lets orOS in, and never stopped. Host commands: `ai.status`, `ai.start`, `ai.install`, `ai.forget`, `ai.gpu` (off: `OLLAMA_VULKAN=0`), `ai.remove`. `OROS_NO_AI=1` hides it. CI downloads the real Ollama and `qwen3:0.6b` on Linux and Windows and checks one answer.

Wi-Fi and Bluetooth (`launcher/sysnet.go`): Wi-Fi is controlled inside orOS as on the stick (networks, password, radio on or off), through NetworkManager's `nmcli` on Linux and the Native Wi-Fi API (`wlanapi.dll`, `net_windows.go`) on Windows. A network Windows knows connects with its saved profile; a new one gets a WPA2/WPA3 personal or open profile; enterprise networks stay with Windows' settings. Passwords are never logged. Bluetooth opens the computer's own settings (`ms-settings:bluetooth`; GNOME, KDE, Cinnamon, Blueman, Blueberry or Xfce on Linux).

Screen lock with Windows Hello or a fingerprint (`launcher/lockbio.go`, `lockbio_windows.go`, `lockbio_linux.go`): with orOS's screen lock on, Settings › Screen lock can turn on unlocking with Windows Hello (fingerprint, face or the Windows Hello PIN) or, on Linux, a fingerprint through fprintd. The System extension asks the host: `bio.state` (`can`: ok, none = nothing enrolled, no-hw; `kind`: hello or finger), `bio.seal` and `bio.open` (the person verifies first, then a 32-byte secret for the page's record comes back), `bio.clear`. orOS keeps a token wrapped with that secret, so the lock opens only with a secret this computer gave after the check. Windows: WinRT's `UserConsentVerifier` through `IUserConsentVerifierInterop`, its prompt over the browser window Chromium names (`--parent-window`); not WebAuthn, no passkey. The secret is sealed with DPAPI for this Windows user. Linux: `fprintd-list` and `fprintd-verify` (any enrolled finger, 60 s), the secret readable only by this user (0600). Both in `lock-bio.json` in the user's folder, at most 16. As the lock itself, it protects the screen, not the disk. CI calls the real `CheckAvailabilityAsync` and DPAPI on Windows.

orOS Bridge (`launcher/bridge.go`): the full edition and the installers carry [orOS Bridge](https://github.com/koulaxizis/oros-bridge) (`bridge/<os>/`, the latest release, checked against its `SHA256SUMS.txt` by `scripts/build.sh`; a release build needs 0.8.0 or newer), so orOS Studio can use the computer's VST3 and CLAP plugins and its sound card (ASIO® on Windows, JACK, PipeWire, PulseAudio, ALSA on Linux) without a separate download. The launcher that serves orOS (the window, or the tray of an installed copy) starts it with `--bundled --allow-origin http://localhost:47800 --code-file <data>/bridge-code`: no window, no console, no updates of its own (`oros-bridge.bundled` lies beside it; a new orOS Portable brings the new bridge), its output in `bridge.log`, and it ends with the server (Linux: `Pdeathsig`; Windows: a job object, so it also ends when the launcher is killed). When a bridge already answers on 127.0.0.1:47621 (one the person installed), that one is used. The pairing code appears over orOS as on orOS USB: the System host answers `ping` with `bridgeCode` and `bridge.code` with the open code. `OROS_NO_BRIDGE=1` starts none. The ASIO module (`oros-bridge-asio.dll`) is GPL-3.0; its licence, sources and the written offer are in `LICENSES/`, `SOURCES.txt` and `WRITTEN-OFFER.txt`. ASIO is a registered trademark of Steinberg Media Technologies GmbH.

White-screen watchdog (`launcher/watchdog.go`): once orOS has painted, the extension pings every 10 s. Where it has pinged before, a main window with no ping within 90 s is ended and started once more with `--disable-gpu`.

### Computer files ("This computer")

On [orOS USB](https://github.com/koulaxizis/oros-usb) (the live stick and orOS installed on a disk) the launcher also gives the orOS Files app the computer's own files: the home folder and the disks opened under `/media/oros` (`launcher/computerfs.go`, API under `/__oros/fs/`). On orOS USB (`OROS_COMPUTER_FILES=1`, set by its session) it is always on. orOS Portable and the desktop apps offer the same on Linux once the user agrees for this computer (`launcher/fsconsent.go`: a stick asks once per computer, the desktop apps are on by default, both can switch it off; the answer is kept in `data/computer-files.json` under a hash of the computer's machine ID). There the disks are the ones udisks opens under `/run/media/<user>` or `/media/<user>`, with the launcher as its own disk helper (`orOS disks`, `orOS mount --dev /dev/sdX1 [--unmount]`, `launcher/hostdisks_linux.go`): partitions of 1 GiB or more with a readable filesystem that the running system does not use; the computer's own NTFS (Windows) disks open read-only. On Windows (`launcher/computerfs_windows.go`) the disks are the fixed and removable drives as `/disks/C`, `/disks/D` and so on (named "Label (C:)"), all open already; the system drive is whole and writable, but Windows' own folders at its top (Windows, Program Files, ProgramData, Recovery and the like) and every file or folder marked hidden or system stay out of sight, and names Windows cannot hold (`<>:"|?*`, a trailing dot or space, CON, NUL, COM1 and the like) are refused. Removing moves to the Windows Recycle Bin (a removable drive has none: 409 `norecycle`); orOS lists no Recycle Bin items itself, `POST op {"op": "recyclebin"}` opens it in Explorer. "Unmount" points to Windows' "Safely remove". The orOS Portable folder and the data folder are never reachable. `GET consent` says `on`, `off` or `ask`; `POST consent {"on": true|false}` keeps the answer; every other call answers 404 `off` until then. `OROS_NO_COMPUTER_FILES=1` turns all of it off.

- **Only orOS may call it:** a random key in an `HttpOnly`, `SameSite=Strict` cookie (new at every start, sent with orOS's pages), `Sec-Fetch-Site: same-origin`, the same Origin, and the `X-Oros-FS: 1` header on everything but plain file reads. Other sites (also in the Internet window, which shares orOS's browser), other localhost ports and other programs are refused.
- **Only the user's files:** `/home/...` is the home folder without names starting with `.` and without `~/oros` (the launcher and browser profiles); `/disks/<name>/...` is a disk while it is mounted. No symbolic link leads out of its place or to a hidden name.
- **Nothing is lost:** writes go to a hidden temporary file, are flushed and renamed; `replace=1` is needed to overwrite and `ifmtime` refuses a file changed elsewhere (412). Removing moves to the freedesktop.org Trash (the home Trash, or the disk's own `.Trash-<uid>`), from where items can be restored or emptied. A move to another disk copies, reads every file back against its SHA-256, and only then trashes the original. A disk is not unmounted while a copy to it runs.
- **Nothing runs:** files are served with `Content-Security-Policy: sandbox` and web pages as plain text. Disks are listed and mounted by the helper in `OROS_FS_HELPER` (`oros-system disks`, `sudo -n oros-system mount --dev /dev/sdX1 [--unmount]`).

| Call | |
|---|---|
| `GET roots` | home and mounted disks, with free and total space and read-only; `os` (`linux` or `windows`), `under: true` (this launcher checks `under=`) |
| `GET list?path=`, `GET stat?path=` | folder entries `{name, path, dir, size, mtime}` |
| `GET raw?path=` | the file (Range requests for video and audio); `X-Oros-MTime` |
| `PUT raw?path=[&replace=1][&ifmtime=ms]` | write the request body |
| `POST op` `{op, path, to, root, id, dev}` | `mkdir`, `rename`, `copy`, `move`, `trash`, `restore`, `purge`, `mount`, `unmount`, `recyclebin` (Windows) |
| `GET trash`, `GET disks` | the Trash items, the disks that can be opened |

**`under=<folder>` (orOS local folders for Claude, LOCAL-1):** on `list`, `stat` and `raw` (GET and PUT) the path must be that folder or inside it (else 403 `notAllowedRoot`), and neither the folder nor any existing part below it may be a symbolic link or a junction (403 `link`); listings leave links out, and a PUT never replaces a file even with `replace=1`. Any other call with `under` is refused. orOS sends it for every read and write of a folder the owner opened for Claude.


### Mail without the relay (Proton Mail Bridge and every provider)

orOS Mail normally reaches mail servers through the orOS relay on the Internet, which cannot reach a server that listens only on this computer, such as [Proton Mail Bridge](https://proton.me/mail/bridge) (IMAP `127.0.0.1:1143`, SMTP `127.0.0.1:1025`, STARTTLS with its own self-signed certificate). For those the launcher gives the orOS page a WebSocket, `/__oros/mail/sock?host=127.0.0.1&port=1143&mode=starttls&pin=<sha256>` (`launcher/mailsock.go`): Mail runs the relay's own IMAP, SMTP and ManageSieve code in the page over it, and the launcher only carries the bytes and does the TLS. The password goes from the page to Bridge on this computer and nowhere else. The relay does not serve Mail to `http://localhost:47800` at all, so in the orOS on the computer every account goes this way (Chris 2026-11-27), also a provider's own server by name: the page talks to `imap.example.com:993` through the launcher and nothing passes through the relay.

- Only the orOS page: the Host check, the cookie `oros_mail` (random at each start, HttpOnly, SameSite=Strict, `Path=/__oros/mail/`, set on orOS pages), an `Origin` equal to the server's own and `Sec-Fetch-Site: same-origin`.
- This computer: `127.0.0.1`, `::1` or `localhost`, any port but the launcher's own, trusted by pin (below).
- A mail server by name, on the mail ports only (993 and 465 `tls`; 143, 587 and 4190 `starttls`): the name is checked like the relay's (no IP literal, no `.local`, `.lan`, `.internal` and similar names), every address it resolves to must be public (never this computer, the local network or a special range) and is dialled as resolved, and the certificate must be valid for that name against the system's roots (else `{"t":"err","code":"tls"}`; no pin). So it is no open proxy. At most 8 connections, closed after 3 minutes without traffic.
- Always TLS: `mode=tls` handshakes at once; `mode=starttls` lets at most 512 bytes go out and 16 KB come back before the page asks for TLS (`{"t":"starttls"}`), enough for a greeting and STARTTLS, too little for any other protocol.
- Trust by pin, on this computer only: the page passes the SHA-256 of the certificate the person confirmed. Without a pin, or with another certificate, the connection ends with `{"t":"err","code":"cert-new"|"cert","fp":"<sha256>"}`, which Mail shows for the person to confirm. The launcher stores nothing.
### Users on one computer or stick

Several people can share one stick or one installed orOS, each with their own orOS: their own data, password, sync account and settings (`launcher/users.go`, `usersapi.go`, `session.go`, sign-in window in `launcher/login/`). Each user is a browser profile of their own (`--user-data-dir`), so orOS and its encrypted sync work unchanged and one user never sees another's data.

- With one user nothing changes: no sign-in window, the profiles stay in `data/profile` and `data/profile-system`.
- Adding a second user (orOS Settings › Users) makes the person already there the owner; they keep those folders as they are, so nothing moves. Every other user gets `data/users/<id>/` (profiles, Internet window, window choice, "This computer" answer). The owner gets a recovery code to write down.
- From then on each start shows the sign-in window, in its own empty profile (`data/login`), so signing in loads nobody's data. One user at a time; Sign out in orOS (or Switch user in the tray) brings the window back. An optional guest signs in without a password into a folder emptied before and after each guest session.
- Passwords: a PIN of 4-12 digits or at least 6 characters, kept only as a PBKDF2-HMAC-SHA-256 hash (600 000 rounds) in `data/users.json`; after 5 wrong tries each try waits (30 s, doubling, up to 15 minutes). The owner adds and removes users, resets their passwords, turns the guest on and can hand the owner role on, each time with their own password. The first user's folders can never be removed.
- On orOS USB each user other than the first also gets a home of their own for Files' "This computer" (`~/oros/homes/<id>`, with the usual folders; the first user keeps the computer's home, where `~/oros` is never shown). A removed user's home is moved into the first user's home as "<name> (removed user)", so no file goes with them; the guest's home is emptied with the guest's folder. The sign-in window has no Close button there (`kiosk` in `state`); the System extension adds Restart and Shut down.
- Honest limit: the password keeps people away from the screen. Someone who reads the stick on another computer can read the profile folders; on orOS USB the stick's encryption (LUKS) covers that, and each user may encrypt their own files (below).
- **Encrypted users (orOS USB only, optional, off by default; `launcher/vault.go`).** A user other than the first may turn on Settings › Users › "Encrypt my files" with their password. At their next sign-in their profiles and their home are copied into an fscrypt folder on the data partition (`<persistence>/oros-vaults/<id>`, made by `oros-system vault-base`; outside the `/home` overlay, which fscrypt cannot pass), every file is compared (size and SHA-256), the links `data/users/<id>` and `homes/<id>` take the old folders' place and the old copy is removed. The folder is open only while that user is signed in; at sign-out and at every start it is locked, for the owner and root too. The key (64 random bytes) is kept only sealed with AES-256-GCM, by the password (PBKDF2-SHA-256, 600 000 rounds) and by the user's own recovery code, shown once; the owner cannot reset an encrypted user's password, the recovery code can (the sign-in window's "Forgot your password?"). Removing an encrypted user deletes their files (nobody else can read them). Turning it off copies the files back the same way at the next sign-in. An interrupted move is undone or finished at the next sign-in; the old copy goes only after the new one is checked and in place. Not for the first user (the start passphrase covers the whole stick) or the guest. Honest limit: what was on the stick before may stay in unused flash blocks until overwritten. Tests: `vault_test.go` (fake file system), `vault_linux_test.go` and `fscrypt_linux_test.go` (real fscrypt, ext4 on a loop device in CI).

| Call (`/__oros/users/`) | |
|---|---|
| `GET state` | `{enabled, me, users[], guest, max, lang, canAdd, recovery, kiosk, vault}` (no hashes; each user's `vault` state) |
| `POST login`, `recover` | the sign-in window: `{id, password}`, `{id, code, password}` (the owner's code, or an encrypted user's own) |
| `POST vault` | `{on, password}`: encrypt my files at the next sign-in (answers the recovery code), or stop |
| `POST signout` | back to the sign-in window once the user's browser closes |
| `POST add`, `remove`, `password`, `rename`, `owner`, `guest` | owner actions carry `auth` (the owner's password); the first `add` carries `ownerName` and `ownerPassword` |
| `GET sizes` | bytes per user folder |

Only pages of this server may call it: the Host check, `Sec-Fetch-Site: same-origin`, the same `Origin` and the `X-Oros-Users: 1` header on every POST.

## Installers

The same launcher and browser also install on a computer (`scripts/build-installers.sh`, built in CI next to the portable zips):

| | File | Installs to |
|---|---|---|
| Windows 10/11 | `orOS-Setup-<version>.exe` (Inno Setup, `packaging/windows/orOS.iss`), per user, no admin rights, Start menu entry, uninstaller; installs [orOS Drive](https://github.com/koulaxizis/oros-drive) too (see below) | `%LOCALAPPDATA%\Programs\orOS` |
| Linux | `orOS-<version>-x86_64.AppImage` (+ `.zsync` for AppImageUpdate), adds its own menu entry on start (`remove-menu` takes it away) | runs from the file |
| Debian/Ubuntu | `oros_<version>_amd64.deb`, `/usr/bin/oros`, desktop entry, AppArmor rule that lets the bundled Chromium use its sandbox on Ubuntu 23.10+ | `/opt/oros` |

An `installed` file next to the launcher switches it to installed mode: the browser profile, the log and app updates go to the user's data folder (`%LOCALAPPDATA%\orOS` or `~/.local/share/oros`, `OROS_DATA_DIR` overrides it), and the launcher serves whichever is newer by `APP_VERSION`, the app the installer brought or the one `update` fetched. The address stays `http://localhost:47800/`, but the profile is separate from a stick's, so data moves between them through Dropbox sync. `scripts/test-installers.sh` and `scripts/test-windows-setup.ps1` install, run and remove each package in CI.

orOS updates itself in every form (`launcher/autoupdate.go`): the installed apps, the stick, and [orOS USB](https://github.com/koulaxizis/oros-usb) when it has a persistence partition (its session sets `OROS_APP_AUTO_UPDATE=1`; without one the home folder lives in memory and every start would download orOS again). At most every 6 hours, while orOS is open, the launcher checks GitHub in the background: a new commit on orOS `main` is downloaded into `app.next` and swapped in at the next start, never under an open window. The download is the archive of exactly the commit GitHub's API named (`archive/<sha>.zip` over HTTPS), and it is kept only when the archive's own comment names that same commit, it holds `index.html` and a `shell.js` with `APP_VERSION`, it unpacks to under 1 GB, and it is not older than the orOS in use (an older one is not downloaded again; a staged copy older than the one in use is dropped at the start). Only regular files are unpacked, without execute bits, never outside the folder, and without `.github`, `android`, `relay`, `extension` and `tests`; the launcher never runs anything from it (it is the web app the browser shows, the same files useoros.online serves). A stick's program (launcher and browser) changes only with a new stick release, and on orOS USB with a system update. The rest of this paragraph is about installed copies. A new release of this repo is downloaded too and checked against its `.sha256` asset: the Windows setup then runs silently at the next start (`/RELAUNCH=1` opens orOS again), the AppImage replaces its own file, the .deb is offered at the next start and installed with `pkexec apt-get install` (the desktop's own password prompt), and a Scoop install leaves new releases to `scoop update`. The Windows setup asks whether to update automatically and writes a `no-auto-update` file in the data folder when you say no; that file, or `OROS_NO_AUTO_UPDATE`, turns it off. Test builds (`0.0.0-<sha>`) never update; on a stick the same `no-auto-update` file in `data/` turns it off. Every check writes one line to `update.log` in the data folder (kept to 64 KB, also in the report zip), because `launcher.log` starts empty with each window and the reason an update failed used to be lost; a check that breaks is tried again after 1 and 3 minutes (a connection cut in the middle of the download right after the computer starts is common), and one that still fails is tried again after 30 minutes instead of 6 hours.

### One package: orOS, orOS Drive and orOS Bridge

An installed orOS brings [orOS Drive](https://github.com/koulaxizis/oros-drive) and [orOS Bridge](https://github.com/koulaxizis/oros-bridge) with it, under one tray icon (Chris 2026-11-17). Bridge is part of orOS (above). Drive stays its own program (its own folder, settings, sign-in, Explorer folder and uninstaller) but is managed by orOS (`launcher/drive.go`, Drive 0.5.0+ `orosdrive manage`): it shows no icon and has no login start of its own, and the orOS tray starts it when it has settings, restarts it if it stops (at most 3 times in 10 minutes), stops it on Quit and shows an **orOS Drive** menu (state, Sync now, Pause or Resume, Settings) and an **orOS Bridge** menu (ready for Studio, the pairing code). When Drive mirrors its first folder, the tray turns Start with the computer on (once), so Drive keeps syncing after a restart. Drive's Dropbox sign-in works while orOS holds port 47800: Drive asks `GET /__oros/drive-signin`, and the server sends a Dropbox answer whose state Drive made (`orosdrive-<port>-<random>`, ports 47811 to 47820) on to `http://127.0.0.1:<port>/oauth/done`, where Drive takes only its own waiting sign-in.

- **Windows:** the setup carries the latest Drive setup (CI downloads it from that repo's latest release and checks it against its `SHA256SUMS.txt`; a release needs Drive 0.5.0+) and installs Drive too, ticked by default, with `/MANAGEDBY=<orOS.exe>`; its settings page then opens for the sign-in. A Drive installed already is updated when the one inside is newer and never made older; an automatic (silent) update of an installed orOS never adds Drive. Uninstalling orOS asks "Also uninstall orOS Drive?": yes runs Drive's own uninstaller (it asks about its settings and never touches the folders); no, or a silent uninstall, runs `orosdrive manage off`, so Drive shows its own icon and starts with Windows again. Drive also lets go by itself when the orOS program it names is gone.
- **Linux:** the AppImage and the .deb carry `drive/linux/orosdrive` (the latest Drive release, checked; a release needs 0.5.0+). A separately installed Drive (`/usr/bin/orosdrive`, its .deb) is used first. An AppImage copies its Drive to `~/.local/share/oros/drive/` so Drive keeps running after the AppImage ends. The menu entry's **orOS Drive** action (`orOS drive`) starts the tray and opens Drive's settings; on Linux a window starts the tray beside it only when Drive is set up (its settings exist).
- **Portable zips and sticks:** no Drive (it belongs to one computer). Live USB and Android are unchanged.
- winget `koulaxizis.orOS` installs the whole package; `koulaxizis.orOSDrive` and the Scoop buckets stay for those who want Drive alone.

### Tray: add or search (installed copies)

`orOS tray` puts the orOS icon in the system tray (`launcher/tray.go`). A click opens a small window, centred on the screen, with orOS's command bar (`http://localhost:47800/__oros-quick#quick-win`, which the server sends on to `/`): type a task and press Enter, or search your orOS data; Escape closes the window. The menu has Add or search, Open orOS, Check for updates, Start with the computer (off until you turn it on: `HKCU\...\Run` value `orOS` on Windows, `~/.config/autostart/oros-tray.desktop` on Linux) and Quit. On Windows an installed orOS also starts the tray with every window when none runs (`launcher/traystart.go`, since 0.8.3): opening orOS from the Start menu or the desktop brings the icon back after a restart, a Quit or an update. The window keeps serving and the tray takes the server over when it closes; Quit with a window open removes the icon at once and keeps the server until that window closes. The tray logs to `tray.log` (the window's `launcher.log` is kept; both go into the System panel's report). `OROS_NO_TRAY=1` starts none. Linux is unchanged. On Windows, Ctrl+Alt+Shift+Space opens the small window from anywhere. The tray keeps the loopback server up, never reads orOS data (it stays in the browser profile) and runs once per user (`tray.lock` in the data folder). It applies a downloaded orOS, or hands over to a new program version, only while no orOS window is open.

Check for updates (EN/EL/DE, since 0.9.7, `launcher/updatenow.go`) does what the Start menu's "Update orOS" (`orOS update`) does, without leaving the tray: it asks GitHub for the newest orOS commit and says "orOS is up to date (version)" when it already runs, swaps in a newer orOS that the background check already downloaded (`app.next`), or else downloads it and swaps it in, also under an open window (its service worker reloads it). The answer comes in a message box (Windows) or a zenity/kdialog/notify-send message (Linux); a failure is written to `update.log`. One update runs at a time, shared with `/__oros/update`. The program itself (launcher and browser) still updates in the background and at the next start.

Window placement (`launcher/window.go`): the main orOS window opens maximised and the small one centred at 640×460. The small window has its own address so the browser keeps its size apart from the main window's; before a browser starts on the profile, the launcher sets only the main window's saved placement in the profile's `Default/Preferences` to maximised (it never writes there while the browser runs, and leaves a file it cannot read alone). On Windows the launcher places the small window in the middle of the screen; where it cannot (Linux, or a browser that runs already), the orOS page centres its own window. Known limit on Linux: a main window opened while the small one is open takes the place last saved, not maximised.

`orOS quick` opens the same small window from a command: the Start menu entry "orOS Add or search", the "Add or search" action of the Linux menu entry, or a keyboard shortcut you set in your desktop's settings (Wayland gives apps no global shortcut). Plain GNOME shows no tray icons without the AppIndicator extension; `quick` works there too. The Windows setup offers "Start orOS in the tray with Windows" (unticked) and its uninstaller stops the tray and removes the Run value.

### orOS Gate open while orOS is closed (opt-in)

Settings › orOS Gate › `Keep the Gate open on this computer while orOS is closed` is off until the owner turns it on (`launcher/gatehost.go`, orOS 7.34+, oros Bible "GATE-HOST"). On an installed copy the tray then starts the same browser headless (`--headless=new`, same profile, no window) at `/?gate-host=<nonce>` while no orOS window is open, so Claude gets live answers and its changes are made at once; it is orOS on your own disk, so nothing new leaves the computer. The page proves itself by the nonce in `gate-host.run` (`GET /__oros/gate-host?n=`), never by its address alone. Opening a window hands over without losing writes: the launcher writes `gate-host.hold`, the background page lets go and writes `gate-host.bye` after the browser has saved, and only then (at most 12 s) is that browser ended; Linux kills only its own process group after checking `/proc/<pid>/cmdline`, Windows only a chrome.exe in its job object. The tray stops it before an update and on Quit and backs off after 3 failed starts (`gate-host.log`). On orOS USB, whose window never closes, the same switch only lets the Gate work behind the screen lock. While the desktop bar (below) is open it keeps the profile, so the background orOS waits until the bar closes. Not offered on a stick that is not installed, with several orOS users on one copy, or with `OROS_NO_GATE_HOST=1`. Dialogs, apps Claude opens on screen and deletions that ask you still wait for a person, and Sensitive work turns it off.

### Smart bar on the desktop (Windows, installed copies)
The tray menu's `Smart bar on the desktop` (off until you tick it; `deskbar.on` in the data folder) opens orOS's own top bar in a thin window of its own (`http://localhost:47800/__oros-bar#bar-win`, sent on to `/`; orOS shows only the menu button, the smart chips, the clock and the date there, titled `orOS bar`) and docks it at the top of the primary screen as a Windows app bar: no frame, no taskbar button, always on top, and maximised windows stay below it (`launcher/deskbar*.go`). Chromium draws its own title bar inside its window (and keeps app windows at least about 80 px high), so the tray measures where the page sits (`Chrome_RenderWidgetHostHWND`) and moves the window until the page alone fills the strip, with the title bar above the screen's edge; it checks again every 2 seconds. `TestWindowsDeskbarChrome` docks a real Chrome window in CI and checks exactly that. The chips are the ones you pick in orOS Settings › Appearance › Top bar, with the look chosen there. A chip, the clock, the date or the menu button opens that app in the main orOS window, or, with none open, asks the tray (`POST /__oros-open`, only from orOS's own page) to open one. The bar comes back by itself 30 seconds after its browser closes while the setting is on; when an update waits, it steps aside so the update can apply; Quit closes it. With users on the computer the bar shows only while someone is signed in. Linux has no desktop bar yet.

## Building

`scripts/build.sh <version>` builds both editions into `out/`, `scripts/build-sticktest.sh` the stick test, and `scripts/fetch-sources.sh` collects the source archives for a release. CI (`.github/workflows/build.yml`) runs the Go tests on every push and PR, uploads the zips as a workflow artifact on `main`, and publishes a GitHub release for `v*` tags. Every download in a release has a `.sha256` beside it (`orOS-Portable-<version>.zip.sha256`, `orOS-Portable-lite-<version>.zip.sha256`, and the same for the setup, AppImage and .deb): `sha256sum -c orOS-Portable-<version>.zip.sha256` on Linux, or compare `Get-FileHash orOS-Portable-<version>.zip` with the file on Windows.

## Making sticks

orOS stays free; a stick only saves people the download and setup. Every
build carries `LICENSES/`, `SOURCES.txt` (the exact source of every program)
and `WRITTEN-OFFER.txt`, and a tagged release attaches the third-party source
archives, so copies sold on sticks meet the source terms of the GPL/LGPL
parts inside ungoogled-chromium.

- `sudo scripts/make-sticks.sh orOS-Portable-<version>.zip /dev/sdb /dev/sdc ...`
  first checks the zip against the `.sha256` beside it (when there is one),
  erases each stick, makes one NTFS partition named `OROS`, copies the full
  edition, then re-reads every file from the stick and checks it against
  `SHA256SUMS.txt`. It writes all sticks in parallel (a powered USB hub helps)
  and refuses anything that is not a removable USB disk up to 256 GB, or that
  holds a system mount. It asks you to type `ERASE` first. Linux only; needs
  `ntfs-3g`. `scripts/test-make-sticks.sh` tests it on loop devices (CI).
- `orOS-sticktest` (release asset, Windows and Linux) checks whether a stick
  is fast enough: copy it onto the stick and run it there. It measures
  sequential write/read, random 4 KiB writes that wait for the disk (what the
  browser profile does all day) and small-file creation, gives a verdict, and
  appends the numbers to `sticktest-results.txt` on the stick. Use it to pick a
  stick model from samples; it does not measure how long the flash will last.

## Notes

- Private browsing: put a VPN extension in the computer's own browser, not in orOS; see [Private browsing](PRIVATE-BROWSING.md) (EN/EL).
- Format the stick as NTFS. On Linux the browser locks its profile with symbolic links, which exFAT and FAT32 cannot store (the launcher then says so), and FAT32 also mounts without execute permission. Windows runs from any of them.
- The Windows launcher is not code-signed, so SmartScreen warns on first run ("More info" → "Run anyway").
- Close the orOS window before removing the stick; pulling it out while the browser writes can corrupt the profile.
- Dropbox sign-in returns to `http://localhost:47800/`, which must be listed as a redirect URI in the orOS Dropbox app.
